### 5.4 HTTP 状态码处理差异

| 维度 | 后端 | 前端 | 差异 |
|-----|------|------|------|
| 业务成功 | 统一 HTTP 200 + R\<T\>.code | HTTP 200 视为成功 | ⚠️ 后端使用 HTTP 200 承载所有业务结果，错误通过 R.code 区分 |
| 401 | OAuth2 Token 无效 | 自动刷新 → 刷新失败跳转登录 | ✅ |
| 403 | 无权限（由 Security Filter 返回） | 无专门处理（走一般错误路径） | ⚠️ 403 前端无差异化处理 |
| 500 | 服务异常 | ElMessage 弹窗 | ✅ |
| 网络错误 | N/A | reject + ElMessage | ✅ |

**⚠️ 风险点**：
1. 后端所有业务异常均通过 HTTP 200 + R.fail 返回，前端通过 `response.data.code` 判断成功/失败。但前端拦截器只在 HTTP !=200 时才弹窗，这意味着 **后端 R.fail() 的响应在 HTTP 200 下不会被拦截器拦截**，需要各业务组件自行判断 `response.data.code !== 200`。
2. 前端 `validateStatus` 设置 200-500 都视为有效响应，不会触发网络错误，所有错误处理依赖业务代码。

### 风险等级说明

- **高**：前后端数据结构不兼容、权限校验不一致、安全漏洞
- **中**：功能未完全对接、路径不一致、缺少关键校验
- **低**：冗余接口、辅助功能未接入、实现方式不同但效果一致

## 二、数据结构对齐

### 2.1 统一响应格式

前后端统一使用 `AjaxResult` 作为响应包装：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": { ... }
}
```

前端 Axios 响应拦截器（`request.js`）在 `code === 200` 时自动解包返回 `res.data`。

分页接口使用 `TableDataInfo` 包装：

```json
{
  "code": 200,
  "msg": "查询成功",
  "rows": [...],
  "total": 100
}
```

| menuName 唯一 | checkMenuNameUnique() | 无 | **⚠️ 后端独有** |
| 外链地址校验 | isFrame=0 时 path 必须以 http(s):// 开头 | 无 | **⚠️ 后端独有** |
| 路由名称唯一 | checkRouteConfigUnique() | 无 | **⚠️ 后端独有** |
| 上级菜单不能是自己 | menuId != parentId | 无 | **⚠️ 后端独有** |

### 4.4 部门管理校验

| 校验项 | 后端规则 | 前端规则 | 状态 |
|-------|---------|---------|------|
| deptName 唯一 | checkDeptNameUnique() | 无 | **⚠️ 后端独有** |
| 上级部门不能是自己 | parentId != deptId | 无 | **⚠️ 后端独有** |
| 停用级联检查 | 包含未停用子部门时不允许停用 | 无 | **⚠️ 后端独有** |
| 停用父部门检查 | 父部门停用时不允许新增子部门 | 无 | **⚠️ 后端独有** |

### 4.5 定时任务校验

| 校验项 | 后端规则 | 前端规则 | 状态 |
|-------|---------|---------|------|
| Cron 表达式 | CronUtils.isValid() | 无前端校验 | **⚠️ 后端独有** |
| 调用目标安全限制 | RMI/LDAP/HTTP 禁止 + 白名单 | 无 | **⚠️ 后端独有** |

### 4.6 校验规则总结

| 模式 | 说明 | 风险 |
|-----|------|------|
| 后端强校验 | 唯一性检查、业务规则校验仅在后端 | 前端不提示，用户体验差 |
| 前端弱校验 | 前端仅做基本格式校验 | 依赖后端返回错误信息 |
| 密码规则动态化 | 后端通过配置项控制密码规则，前端通过 `usePasswordRule()` 适配 | 设计合理 |

## 八、结论与建议

### 8.1 整体评价

RuoYi-Vue3 前后端接口契约**整体一致性较高**。核心业务模块（用户、角色、菜单、部门、配置、字典、岗位、通知）的接口路径、方法、参数、权限标识均正确对齐。

### 8.2 主要发现

1. **`/logout` 接口缺失**（D-01）：前端调用但后端未实现。考虑到 RuoYi 的 JWT + Redis 架构，前端退出时清除本地 Token 即可实现退出效果。建议：要么移除前端 `/logout` 调用改为纯前端操作，要么在后端补充实现以支持服务端的 Token 清理和审计日志记录。

2. **`monitor:operlog:query` 权限标识孤立**（D-13）：前端使用了此后端不存在的权限标识。建议在后端 SysOperlogController 中添加对应接口，或在前端改为使用 `monitor:operlog:list` 权限。

3. **唯一性校验仅在后端**（D-17）：角色名称、角色权限、菜单名称、部门名称等唯一性检查均仅在后端实现。建议在前端表单中增加异步校验（如 blur 时调用后端检查接口），提升用户体验。

4. **批量删除前端仅传单值**（D-10, D-11）：后端 DELETE 接口设计为批量删除（`Long[]` 数组），前端 API 函数仅传递单个 ID。虽功能可用，但前端未充分利用后端的批量能力。建议在表格多选场景下使用批量删除。

### 8.3 风险等级

| 风险等级 | 项数 | 说明 |
|---------|------|------|
| 高 | 0 | 无阻塞性问题 |
| 中 | 2 | D-13（孤立权限）、D-17（唯一性无前端预校验） |
| 低 | 10+ | 未使用接口、校验宽松、代码不严谨等 |

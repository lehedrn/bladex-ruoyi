## 改进方案

```
### 0. 项目特征识别（自动裁剪）

根据用户提供的代码目录，按以下层级检测：

层级1：判断项目类型
- 有服务端代码（Controller/Web层 + 业务逻辑层 + 数据层）→ Java 后端项目
- 有前端代码（Vue 组件 + 路由 + 状态管理）→ Vue 前端项目
- 两者都有 → 全栈项目

层级2：判断技术栈特征
- Java 后端：
  - 有 Starter/AutoConfiguration/spring.factories → 启用底层架构子模块
  - 有 Controller/Service/Mapper → 启用后端分析子模块
- Vue 前端：
  - 有 vue 文件 + 构建工具配置（vite.config / vue.config / webpack.config）→ Vue 前端项目
  - 有 router/index + 路由配置 → 动态路由项目
  - 有 store/ + Vuex 或 Pinia → 状态管理项目

层级3：判断是否启用接口契约
- Java 后端定义了 HTTP 接口 + Vue 前端有 API 调用封装 → 启用接口契约子模块
```

**关键变化**：
- 用"有没有这类文件"代替"是不是叫这个具体名字"
- 构建工具用 `vite.config / vue.config / webpack.config` 覆盖主流选项

- 一个小型项目，后端可能只有 5 个 Controller，没必要拆 4 个 subagent
- BladeX 这种大型项目，Service 层可能有 200+ 文件，4 个 subagent 也不够

**改进思路**：不预定义 subagent 表，改为**动态拆分**。

父 Agent 启动后：
1. 先做快速扫描，评估代码规模和复杂度
2. 按子模块 prompt 中定义的分析维度，每个维度独立启动一个 subagent
3. 如果某个维度的代码量特别大，再进一步拆成多个 subagent（如按业务模块拆分 Service 分析）
4. 代码量小的话可以不拆 subagent，直接单 Agent 分析

## 问题 2：并行启动的瓶颈

当前的 Phase 设计确实是瓶颈在于接口契约——必须等前后端都完成。但仔细看，Phase 1 的三个 Agent **完全可以并行**，真正的串行只有 Phase 2。

实际执行时间线应该是这样的：

```
时间轴 →

总控: [特征识别]
Agent架构:  ━━━━━[底层架构分析]━━━━━━━━━┓
Agent后端:  ━━━━━[后端业务分析]━━━━━━━━━━━━━┫
Agent前端:  ━━━━━[前端应用分析]━━━━━━━━━━━━━┣━━━┓
                                           ┃    ┃
Agent契约:                                   ┗━━━╋━━━[接口对齐分析]━━━┓
                                                  ┃                  ┃
总控:                                            ┗━━━[业务规则汇总+输出文档]
```

所以三个 Agent 在 Phase 1 本来就是并行的，瓶颈只在 Phase 2。这个瓶颈没法消除（接口对齐必须先有前后端结果），但 Phase 1 并行已经最大化了。

## 改动方案

把 `agent-teams.md` 的 subagent 部分从**静态表格**改为**动态拆分规则**：

```markdown
### subagent 动态拆分规则

每个父 Agent 启动后按以下流程动态决定 subagent：

1. **快速扫描**：读取目标目录的文件数量和目录结构
2. **按维度拆分**：子模块 prompt 中定义了 N 个分析维度，每个维度启动一个 subagent
3. **按需二次拆分**：若某维度代码量>50 个文件或>3 个子包，按业务模块/包名进一步拆分
4. **小项目不拆**：若目标代码<20 个文件，直接单 Agent 完成，不派 subagent
```

同时更新每个 Agent 的定义，去掉写死的 subagent 表，改为列出"分析维度"。

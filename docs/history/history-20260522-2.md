## 问题3：Phase 1并行Agent之间存在信息隔离

### 现状

`agent-teams.md` 的 Phase 1 描述：

```
Phase 1（并行 3 路，互不依赖）:
  Agent A: 底层架构分析
  Agent B: 后端分析
  Agent C: 前端分析
```

但实际后端分析需要底层架构的信息（如全局异常处理机制、租户拦截器、通用工具类等），否则分析会重复或遗漏。

### 具体问题

| 场景 | 问题 |
|------|------|
| 后端分析时 | 不知道底层框架已经定义了全局异常处理器，可能在 Controller 层重复分析 |
| 后端分析时 | 不知道底层框架的租户拦截器机制，权限分析不完整 |
| 前端分析时 | 不受影响（前端分析不依赖底层架构） |

当前虽然加了"agent-backend 可选读取 agent-architecture 中间输出"，但和"互不依赖"矛盾，且执行时机不明确。

### 改进方案

改为**明确的依赖关系**，不再用"可选"这种模糊表述：

```
Phase 1（并行启动，部分依赖）:
  ├── agent-architecture（无依赖，最先启动）
  ├── agent-frontend（无依赖，与 architecture 并行启动）
  └── agent-backend（依赖 architecture 完成，在其完成后启动）
```

具体执行流程：

```
1. 同时启动 agent-architecture 和 agent-frontend
2. 等待 agent-architecture 完成
3. agent-backend 启动时，先读取 architecture 的分析报告，再进行自身分析
4. 等待 agent-backend 和 agent-frontend 都完成，进入 Phase 2
```

这样实际执行时间线是：

```
时间轴 →
architecture: ━━━━[分析]━━━━┓
frontend:     ━━━━[分析]━━━━━━━━━━━┫
                             ┃
backend:                    ┗━━━[读architecture报告+分析]━━━┓
                                                          ┃
contract:                                                  ┗━━━[接口对齐]━━━┓
```

总耗时 = max(architecture, frontend) + backend分析 + contract + 汇总

### 改动位置

- `agent-teams.md` 的"阶段划分"和"并行策略"章节
- `系统分析.md` 中如果引用了 Phase 1 的描述，也需要同步

### 影响

- 后端分析质量提高（能复用底层架构的结论）
- 总耗时略有增加（backend要等architecture），但backend本身分析时间会缩短（不需要重复分析基础设施）

你觉得这个方向可以吗？

## 问题4：接口契约的串行瓶颈

### 现状

```
Phase 1: 3个Agent并行
Phase 2: agent-contract 串行（必须等Phase 1完成）
Phase 3: 总控汇总
```

接口契约必须等前后端分析都完成后才能执行，这是逻辑依赖，无法消除。

### 具体问题

当前 agent-contract 在 Phase 2 启动后，需要：
1. 读取后端分析报告
2. 读取前端分析报告
3. 从两份报告中提取接口清单
4. 逐一比对
5. 生成差异报告

其中步骤3（提取接口清单）是重复劳动——后端和前端分析时已经梳理过各自的接口了，Phase 2 还要再提取一遍。

### 改进方案

**核心思路**：让 Phase 1 的 Agent 在分析时就把接口信息按统一格式输出，Phase 2 只做比对。

具体改动：

**1. 在 `_后端分析.md` 和 `_前端分析.md` 的输出要求中增加：**

```
### 接口清单输出格式（供接口契约对齐使用）

分析报告末尾必须附带以下格式的接口清单（独立章节，便于 Phase 2 直接消费）：

#### 后端接口清单
| 模块 | HTTP方法 | 接口路径 | 权限标识 | 入参 | 返回值 | 来源文件 |

#### 前端API调用清单
| 模块 | HTTP方法 | 调用路径 | 对应API文件 | 调用位置（组件/页面） |
```

**2. 在 `_接口契约.md` 中简化输入读取：**

```
### 输入来源（模式 B）
直接从后端分析报告的"后端接口清单"章节和前端分析报告的"前端API调用清单"章节读取，无需重新提取。
```

**3. agent-contract 的工作范围缩小为：**

```
1. 读取两份接口清单（直接消费，无需提取）
2. 逐条比对（路径/方法/参数/权限）
3. 生成差异报告 + 对齐矩阵
```

### 改动位置

| 文件 | 改动 |
|------|------|
| `_后端分析.md` | 输出文档结构增加"接口清单"章节，定义表格格式 |
| `_前端分析.md` | 输出文档结构增加"API调用清单"章节，定义表格格式 |
| `_接口契约.md` | 输入来源改为"直接读取清单章节"，删除"从报告中提取接口"的描述 |
| `agent-teams.md` | agent-contract 的工作描述简化为"比对"而非"提取+比对" |

### 影响

- Phase 2 执行时间缩短（省去了重新提取接口的步骤）
- 接口清单格式统一，便于自动化比对
- 串行瓶颈依然存在，但执行效率提升

你觉得这个方向可以吗？

## 问题6：章节编号连锁断裂

### 现状

每次新增/删除一个章节，需要手动调整：
1. 本文件后续所有章节编号（如 §5 → §6）
2. 子模块内部对该章节的子引用（如 5.1 → 6.1）
3. 该子模块"可视化输出"章节中对其他章节的引用
4. `agent-teams.md` 中对应 Agent 的维度映射表
5. 输出文档结构中对章节的引用

历史对话中仅因为新增一个"国际化"章节，就导致了 4 处连锁编号断裂。

### 具体问题

当前各子模块都使用**数字章节编号**（如 `## 5. 业务规则挖掘`），所有引用都用"第5章"这种数字形式。一旦章节插入/删除，所有引用都会失效。

### 改进方案

**方案A：改用命名引用**

将所有跨引用从"第X章"改为"见[章节名]"：

```
之前：参见第5章"业务规则挖掘"
之后：参见[业务规则挖掘]章节
```

优点：插入/删除章节不影响引用
缺点：需要AI理解命名引用，可能不如数字直观

**方案B：保持数字编号，增加检查清单**

在每次修改提示词后，执行以下检查：
```
□ 各子模块章节编号是否连续（无跳号、无重复）
□ 子模块"可视化输出"中的章节引用是否对应实际章节号
□ agent-teams.md 维度表中的章节引用是否对应实际章节号
□ 总控中引用子模块章节的地方是否正确
```

**方案C：子模块的"可视化输出"和"输出文档结构"放在固定章节**

将这两个章节固定为倒数第二章和最后一章，无论中间插入多少分析章节，这两个章节的章节号永远是 `N-1` 和 `N`。引用时只需要说"可视化输出章节"和"输出文档结构章节"，不需要数字。

### 我的建议

**推荐方案B+C组合**：
- 方案C解决最高频的问题（可视化输出和输出文档的引用）
- 方案B作为兜底检查，成本低

不改引用格式（方案A），因为数字引用对AI来说更直观、更容易理解。

你觉得这个方向可以吗？

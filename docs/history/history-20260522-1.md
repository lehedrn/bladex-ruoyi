## 系统分析提示词存在的问题

根据历史对话中的实际迭代和反复自检，可以将问题归纳为以下几个维度：

### 一、架构设计层面

**1. 单文件无法覆盖多种项目类型**
最初一份提示词试图同时分析后端、前端、底层框架，导致前端分析时输出质量一般。后续通过拆分为"总控 + 4 个子模块"解决，但这个演进过程说明初始设计对前端/底层框架的分析维度考虑不足。

**2. Agent Teams 编排过于死板**
最初写死了每个 Agent 拆成几个固定的 subagent（如 `subagent-controller`、`subagent-service`），但实际代码量差异很大——小型项目没必要拆，大型项目可能不够用。后续改为动态拆分规则。

**3. Phase 1 并行 Agent 之间存在信息隔离**
后端分析需要底层架构的信息（如全局异常拦截器），但三路完全并行无法共享。后来加了"信息同步点"（agent-backend 可选读取 agent-architecture 中间输出），但"互不依赖"和"可选读取"的表述一度矛盾。

**4. 接口契约的串行瓶颈无法消除**
接口契约必须等前后端都完成才能执行，这是整个并行方案的唯一串行瓶颈，无法优化。

### 二、内容一致性层面

**5. 五分类表格在 4 个子模块中重复**
总控定义了一套业务规则五分类（计算/流程/约束/权限/异常），但每个子模块又各自重复了一遍完整表格。定义不一致时有漂移风险，后来改为各子模块只保留示例、引用总控定义。

**6. 章节编号连锁断裂**
新增一个章节（如国际化）后，后续所有章节编号需要连锁调整，且子模块内部的交叉引用、agent-teams 的维度映射、输出文档归属都要同步更新，非常容易遗漏。

**7. 交叉引用不一致**
子模块中引用总控章节号、agent-teams 中引用子模块章节号、输出文档中引用分析章节——多处引用经常出现指向错误的情况。

**8. 输出文档命名冲突**
03 号文档（数据模型使用手册）在前端项目时实际内容是"组件与状态"，文件名语义不符。后来改为根据项目类型确定文件名（03a/03b/03c），但组合规则的实现一度不清晰。

### 三、可执行性层面

**9. drawio skill 依赖问题**
提示词中声称"drawio 是一个已安装的 Agent Skill"，但实际环境中可能未安装。WSL2 环境下 drawio CLI 频繁报 GPU/EGL 错误，snap 包还可能损坏。最终不得不 fallback 到 Python 脚本解析 XML 生成 SVG。

**10. drawio 导出路径问题**
导出命令中的文件名缺少完整路径，实际执行时需要先 `cd` 到图表目录。后来加了 `cd` + glob 批量导出解决。

**11. SVG 文件名与 markdown 引用不匹配**
drawio CLI 导出为 `xxx.drawio.svg`，但 markdown 引用的是 `xxx.svg`，导致所有图片无法加载。

**12. Agent 工具 `description` 参数缺失**
实际执行时首次调用 Agent 忘了加必填的 `description` 字段，三个并行 Agent 全部报错。

**13. "引入子模块"机制不清**
总控多处写"引入子模块"，但 AI 无法确定是 Read 拼接、分发 Agent、还是参考查阅。

### 四、分析维度缺失（已逐步补齐）

**14. 多租户分析缺失** — BladeX 和 RuoYi 都有多租户能力，但初始提示词中没有专门的分析引导。

**15. 中间件分析缺失** — Redis 缓存策略、消息队列消费幂等、连接池配置等关键信息没有系统化分析引导。

**16. 国际化（i18n）分析缺失** — 错误消息国际化、前端 i18n Key 管理、前后端错误码对齐完全没有提及。

**17. 业务规则分析薄弱** — 初始只是让各模块"列出规则"，没有定义如何提取、如何分类、如何交叉验证。

### 五、实操风险

**18. 中等项目过度分析风险**
提示词没有项目规模判断，一个小项目也会被要求追踪调用深度 ≥3 层、分析全部设计模式，产生大量无意义的输出。

**19. 图表目录竞态条件**
多个 Agent 并行写入同一个 `diagrams/` 目录，可能产生文件名冲突。后来改为按模块前缀分目录。

**20. Phase 3 汇总不可执行**
"合并规则""构建依赖图""生成文档"缺乏具体操作步骤和模板，AI 不知道如何落地。

**21. 模式 A（单线程）下接口契约无 fallback**
接口契约模块在模式 B 下从 Agent 报告读取，但模式 A 下没有定义如何获取前后端接口信息。

---

这些问题在历史对话中经过多轮自检和修复，大部分已经解决。但从演进过程可以看出，提示词系统的主要痛点集中在：**多模块一致性维护、章节编号管理、Agent 并行编排的复杂性、以及外部环境依赖（drawio）的脆弱性**。

### 问题2：Agent Teams编排过于死板

**现状**：已改为动态拆分规则（文件<20不拆，>50二次拆分）

**当前状态**：✅ 已解决

**改进方案**：当前的动态拆分规则基于文件数量阈值（<20不拆，>50二次拆分）。但文件数量不是唯一指标——有些项目文件少但逻辑复杂。

**建议**：增加复杂度判断维度：
- 文件数量（当前）
- 业务模块数量（如Controller数量>10个）
- 调用链深度（是否有>3层的调用链）
- 综合评分 = 文件数 + 业务模块数×5 + 调用链深度×10

### 问题3：Phase 1并行Agent之间存在信息隔离

**现状**：加了"信息同步点"（agent-backend可选读取agent-architecture中间输出）

**当前状态**：✅ 已解决（但表述曾出现矛盾）

**改进方案**：当前是"可选读取"，这意味着：
- agent-backend 可以选择等待或不等待
- 没有明确的依赖关系定义

**建议**：改为明确的"可选依赖"：
```
Phase 1 执行顺序：
- agent-architecture 和 agent-frontend 完全并行，无依赖
- agent-backend 依赖 agent-architecture（可选）：
  - 如启用：等待 agent-architecture 完成，读取其中间输出
  - 如不启用：独立执行（适用于无底层框架的纯业务项目）
```

### 问题4：接口契约的串行瓶颈无法消除

**现状**：这是架构决定的，无法优化

**当前状态**：⚠️ 无法解决，只能接受

**改进方案**：这个瓶颈是逻辑依赖，无法消除。但可以优化执行效率：
- 在Phase 1的Agent执行时，就要求它们按统一格式输出接口信息（而不是等Phase 2再提取）

## 问题2：Agent Teams编排拆分规则不够灵活

### 现状

当前 `agent-teams.md` 中的 subagent 拆分规则是基于**文件数量阈值**：

```
- 文件 < 20：不拆 subagent
- 文件 20-50：按子模块定义的分析维度拆分
- 文件 > 50：二次拆分（按业务模块/包名）
```

### 具体问题

文件数量不是唯一指标，存在两种误判：

| 场景 | 文件数 | 实际复杂度 | 当前行为 | 问题 |
|------|--------|-----------|---------|------|
| 工具类库 | 30个 | 低（纯工具方法，无业务逻辑） | 拆5个subagent | 过度拆分 |
| 核心业务系统 | 45个 | 高（15个Controller，调用链深4层，5个业务模块） | 只按维度拆，不二次拆 | 拆分不足 |

### 改进方案

引入**综合评分**替代单一文件数阈值：

```
### subagent 动态拆分规则

父 Agent 启动后按以下流程决定 subagent：

1. **快速扫描**：读取目标目录，收集以下指标：
   - 文件总数（.java/.vue/.ts/.js）
   - 业务模块数（有独立 Controller 或 View 的模块）
   - 最大调用链深度（或组件嵌套深度）

2. **计算复杂度评分**：
   - 文件数 × 1 分
   - 业务模块数 × 10 分
   - 调用链深度 ≥ 3 层，每深一层 × 5 分

3. **按评分决定拆分**：
   | 评分 | 策略 |
   |------|------|
   | < 30 | 不拆 subagent，单 Agent 完成 |
   | 30-80 | 按子模块定义的分析维度拆分 |
   | > 80 | 按维度拆分 + 大模块二次拆分 |

4. **二次拆分规则**（仅评分 > 80 时）：
   - 某维度下文件数 > 30 或子包 > 3 个 → 按子包拆分
   - 某业务模块调用链深度 > 3 层 → 按调用链分段拆分
```

### 改动位置

- `agent-teams.md` 中的"subagent 动态拆分规则"章节
- 不需要改其他文件

### 影响

- 小项目不会被过度拆分
- 大项目会得到更细粒度的并行
- 评分阈值后续可调
